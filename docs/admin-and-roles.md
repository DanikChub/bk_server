# Администратор, сотрудники и роли

Состояние реализации на 17 ноября 2026. Ниже описан новый сервер.

## Первый главный администратор

Готового общего пароля в репозитории нет. Если администратор уже существует
в перенесённой БД, используется его прежний логин/пароль; старые Identity хеши
поддерживаются. Для создания нового администратора на подготовленной базе
задать в `frontend/.env.local`:

```dotenv
BOOTSTRAP_ADMIN_USERNAME=admin
BOOTSTRAP_ADMIN_EMAIL=your-email@example.com
BOOTSTRAP_ADMIN_PASSWORD=<свой уникальный пароль не короче 12 символов>
```

Из frontend выполнить `npm run db:migrate`, затем `npm run db:bootstrap`.
Скрипт не перезаписывает существующего администратора и не сбрасывает его пароль.
После создания убрать BOOTSTRAP_ADMIN_PASSWORD из окружения.

Открыть `/client/login`, ввести заданные логин/пароль, поле организации оставить
пустым. Администратор и сотрудники относятся к host, то есть `TenantId=null`.
После входа откроются `/tickets`. Для клиента организация обязательна: принимается
имя tenant, краткое имя профиля или UUID организации.

## Какие роли есть

| Роль | Как появляется | Поведение |
| --- | --- | --- |
| `admin` | Bootstrap или существующая БД | При TenantId=null имеет все права нового сервера, управляет ролями и администраторами |
| `Клиент` | Создание организации/клиента | Tenant-роль с клиентскими grants; доступ только своей организации, черновики только автора |
| Остальные | Существующая БД или создание через API | Доступ определяется grants, одного имени роли недостаточно |

Полный список ролей конкретной установки находится в БД. Автоматически создаются
только указанные системные роли. Не следует считать старые названия должностей
готовыми наборами прав: например, для удаления заявки проверяются одновременно
`Ticket.Delete` и роль `admin` либо `Руководитель отдела продаж`.

## Добавление сотрудников и администраторов

На `/employees` есть «Добавить»: логин, начальный пароль, email, ФИО и должность.
Сейчас форма не назначает роли. Созданный сотрудник без grants не получит доступ
к рабочим операциям. Полный UI управления ролями ещё не сделан; использовать API
в браузере под главным администратором. Запросы отправляются на тот же origin.

Пример для консоли браузера, открытого на странице приложения:

```javascript
async function api(path, method = 'GET', body) {
  const response = await fetch('/api/v1/' + path, {
    method, credentials: 'same-origin',
    headers: body === undefined ? undefined : {'Content-Type':'application/json'},
    body: body === undefined ? undefined : JSON.stringify(body)
  });
  const result = await response.json();
  if (!response.ok) throw new Error(result.error?.message || 'Ошибка API');
  return result;
}
await api('roles'); // host-роли; возвращается массив
await api('employees'); // сотрудники; возвращается {items,totalCount}

// UUID из ответа employees, поле Id (не ProfileId).
await api('employees/UUID-ПОЛЬЗОВАТЕЛЯ/roles', 'POST', {roles:['admin']});
```

Этот запрос заменяет весь набор ролей пользователя, отзывает его сессии;
ему нужно войти снова. Главный администратор не может снять собственную роль admin.
Другой host-пользователь с admin также становится полным администратором.

## Настройка ограниченной роли

```javascript
const role = await api('roles', 'POST', {name:'Специалист', tenantId:null});
await api('roles/' + role.Id + '/permissions', 'POST', {permissions:[
  'Ticket', 'Ticket.Get', 'Ticket.Edit',
  'TicketHistory.Get', 'TicketHistory.Create',
  'TicketAttachments.Get', 'TicketAttachments.Create'
]});
await api('employees/UUID-ПОЛЬЗОВАТЕЛЯ/roles', 'POST', {roles:['Специалист']});
```

Это ограниченный пример для заявок/переписки, не готовая полная роль для всех
разделов интерфейса. Для назначения исполнителей нужны
`SpecialistManagement.Get/Create/Delete`; для справочников и остальных операций
нужны дополнительные grants соответствующих сервисов. Точные проверки находятся
в `frontend/src/server/modules` и `auth/session.ts`. Произвольная строка права
не добавляет новую возможность, если сервер её не проверяет.

Список назначенных разрешений роли: `GET /api/v1/roles/:id`.
`POST /roles/:id/permissions` заменяет полный набор прав этой роли.

## Клиенты, блокировка и пароль

Создать организацию на `/customers`, затем пользователя на `/users`, выбрав
организацию. Сервер автоматически назначит tenant-роль `Клиент`.
Нельзя делать клиента главным администратором назначением host-роли.

Для сотрудника доступны:

```javascript
await api('employees/UUID-ПОЛЬЗОВАТЕЛЯ/active','POST',{active:false});
await api('employees/UUID-ПОЛЬЗОВАТЕЛЯ/password','POST',{password:'СВОЙ-НОВЫЙ-ПАРОЛЬ'});
```

Для клиентского пользователя те же операции через `users/:id/...`.
Пароли не отправлять в чат, документацию или GitHub. Для тестирования разных ролей
использовать разные профили браузера/приватные окна: одна cookie-сессия соответствует
одному аккаунту.
